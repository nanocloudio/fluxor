# dns Module

DNS Server PIC Module

## Files

- `manifest.toml`
- `mod.rs`
- `sdk/contracts/net/dns_wire.rs` (mounted) — the message codec: header,
  names with compression, question, resource records. Shared with the `ip`
  module's stub resolver; this module stays a server.

## Interface (manifest)

```toml
version = "1.0.0"
hardware_targets = ["rp2350"]

# Network transport: wired to the IP / transport stack via NetProto.
[[ports]]
name = "net_in"
direction = "input"
content_type = "NetProto"

[[ports]]
name = "net_out"
direction = "output"
content_type = "NetProto"
```

## Parameters

- `host`
- `port`
- `ttl`
- `upstream`
- `upstream_port` (destination port for forwarded queries, default 53 —
  lets a delegation listener on a non-standard port be the upstream)
- `dns64_prefix` (absent by default; `"<ipv6>/96"` — only /96 is admitted,
  anything else refuses construction) and `dns64_exclude` (repeatable
  `"a.b.c.d/n"`; absent means every non-global IPv4 range is excluded, and
  the well-known prefix `64:ff9b::/96` excludes them whatever the list says)
- `update_zone` (the one zone served authoritatively and open to TSIG-signed
  UPDATE), `update_durability` (`volatile` | `durable`, required with
  `update_zone`), `update_allow` (repeatable
  `"keyname=name-suffix,TYPE,..."`, `*` for every type; the key is vault label
  `dns/tsig/<keyname>` and is never generated by the module) and
  `update_path` (the file a durable generation is committed to through the
  `fs` contract, default `dns_zone.fxz`)
- `upstream_transport` (`udp` | `tls` | `https`, default `udp`) and, for the
  two encrypted forms, `upstream_authority` (`host[:port]`, defaulting to
  port 853 for TLS and 443 for HTTPS; required for both). `upstream_path` is
  the DoH endpoint, default `/dns-query`, since the path is server-specific.
- `dnssec` (`off` | `validate`, default `off`) and `dnssec_anchor`
  (repeatable; presentation format, the text `dig DNSKEY` prints, for
  example `"example.com. 257 3 13 <base64 key>"`)

## Supported profile

- Exactly one question per query (`QDCOUNT == 1`). Local answers are
  constructed from the header plus that question; nothing trailing the
  question is echoed.
- Names up to `MAX_NAME_LEN` (255) bytes, labels up to `MAX_LABEL_LEN` (63) —
  both registered in `docs/architecture/limit_register.md`.
- Forwarded queries carry a CSPRNG-drawn upstream transaction id, not the
  client's. An upstream answer is relayed only when it arrives from the
  configured upstream address and port with QR set, the expected opcode, and
  exactly the forwarded question, against a live pending slot.
- `MAX_PENDING` (8) forwarded queries may be outstanding. With every slot live,
  a new query is answered SERVFAIL; accepted work is never displaced.
- An encrypted upstream has no cleartext fallback: with the leg down a
  forwarded query is answered SERVFAIL rather than sent over UDP/53. What it
  buys is confidentiality and integrity of the query. Whether the upstream is
  also authenticated is the wired `tls` instance's `peer_auth` and `trust`
  configuration, which this module cannot see.
- Under `dnssec: validate`, a signature is checked only when the RRSIG's
  signer names a zone given as a `dnssec_anchor`. An answer signed by any
  other zone is relayed without the AD bit rather than claimed as checked,
  and an answer whose signature fails is refused with SERVFAIL.
- An anchor is used as the verifying key directly: no DS or DNSKEY chain is
  walked. So the anchor must be the key the zone actually signs its answers
  with — anchoring a key-signing key of a zone that signs with a separate
  zone-signing key makes every answer for it fail. Only the first anchor
  given for a zone is consulted, so a second entry does not carry a
  rollover.
