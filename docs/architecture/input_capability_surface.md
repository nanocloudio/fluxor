# Input Capability Surface

Fluxor's input architecture rests on two layered concepts:

1. a **surface family** — typed channel content the graph carries, one
   content type per input class;
2. a **role discipline** — sources emit raw source events, mapper
   modules own application meaning, and consumers read the resolved
   surface only.

This document is the input peer of `av_capability_surface.md`,
`protocol_surfaces.md`, and `monitor-protocol.md`. The guiding rule is
the one stated in [vision.md](../vision.md): a button is not a GPIO pin, a keyboard
is not a Bluetooth peripheral. Input providers describe what happened
on a labelled control; application meaning belongs in mapper modules
or graph configuration.

---

## 1. Canonical surface family

Source: `contracts/src/lib.rs` (`CONTENT_TYPES`).

Input pipelines move data on channels typed by `content_type`. One
content type exists per input class, so a consumer reads the same wire
shape regardless of which producer is on the other end:

| Surface             | Carries                                      | Typical producers                                              |
|---------------------|----------------------------------------------|----------------------------------------------------------------|
| `KeyEvents`         | Keyboard transitions (logical + physical key) | `wasm_browser_keyboard`, `linux_display` (window), hardware scan-code readers |
| `PointerEvents`     | Unified mouse / touch / stylus events, and the wheel | `wasm_browser_pointer`, `linux_pointer`, `linux_display` (window), touchscreen drivers |
| `TextEvents`        | Committed text, compositions, deletions and selection moves from the platform's text machinery | `wasm_browser_accessibility`, `linux_display` (window) |
| `AccessibilityTree` | The controls an application draws, as a tree of nodes | the application itself                                    |
| `AccessibilityActions` | What assistive technology or a pointer did to a mirrored control | `wasm_browser_accessibility`                      |
| `GamepadEvents`     | Gamepad state snapshots                      | `wasm_browser_gamepad`, `wasm_browser_touch_gamepad_overlay`   |
| `MidiEvents`        | Pre-decoded MIDI 1.0 channel-voice events    | `wasm_browser_midi_in`, `linux_alsa_midi`                      |
| `OctetStream` (button wire) | Debounced single-button transitions  | `modules/drivers/button`, `flash_rp` (BOOTSEL), `wasm_browser_button` |
| `FmpMessage`        | Semantic commands after mapping              | `modules/foundation/gesture`, `wasm_browser_action`                    |
| `SurfaceTraits`     | Environment-plane snapshots (viewport, modality, audio config) | `wasm_browser_surface_traits`, `linux_surface_traits` |
| `InputBinaryState`  | Keyboard-state snapshots on a single port    | `wasm_browser_dom_input`                                       |
| `InputEvent`        | Generic surface: a driver's own record shape, for a device that fits none of the per-class surfaces | `gt911` touch driver             |
| `GestureMatch`      | Recognised gesture pattern                   | gesture recognisers                                            |

Wiring edges that mismatch surfaces fail the build with a content-type
mismatch from `tools/src/config/manifest.rs::validate_wiring_types`.
The surface ID table is `CONTENT_TYPES` in `contracts/src/lib.rs`,
re-exported through `tools/src/manifest.rs`.

A graph wires a per-class surface wherever one applies; `InputEvent`
carries only a device whose events fit none of them.

## 2. Payload contracts

Source: `crates/fluxor-abi/src/contracts/input/`. Each file is the wire contract
its producers and consumers both include, so the two cannot drift.

### `KeyEvents` — `crates/fluxor-abi/src/contracts/input/key.rs`

Fixed 8-byte frame modelled on the W3C UIEvents `KeyboardEvent` spec:

```text
[msg_type: u8] [event_kind: u8] [modifiers: u8] [flags: u8]
[key_code: u16 LE] [scan_code: u16 LE]
```

`key_code` is the logical key after keymap; `scan_code` is the
physical code (USB HID usage or evdev keycode). Games and emulators
key on `scan_code` (layout-independent); terminals and text editors
key on `key_code`.

Byte 3 is a flags byte, with two bits allocated and the rest zero:

| Flag | Value | Meaning |
|---|---|---|
| `KEY_REPEAT` | `0x01` | a key-down generated by autorepeat |
| `KEY_TEXT`   | `0x02` | the key's effect arrived on `TextEvents`: an insert, a deletion, a paste |

A consumer reads the record through `key::decode`, which names the two
flags as fields and refuses a record with an unallocated flag bit; it
does not index the byte. The rule that keeps a key from acting twice is
in [Keys and text](#keys-and-text-never-twice) below.

### `PointerEvents` — `crates/fluxor-abi/src/contracts/input/pointer.rs`

Fixed 16-byte frame modelled on the W3C Pointer Events spec: one
unified surface for mouse, touch, and stylus.

```text
[msg_type: u8] [pointer_id: u8] [event_kind: u8] [buttons: u8]
[modifiers: u8] [wheel_unit: u8] [pressure: u16 LE]
[x: i16 LE] [y: i16 LE] [dx: i16 LE] [dy: i16 LE]
```

Event kinds: down, up, move, cancel, enter, leave, relative move and
wheel. `pointer_id` lets multiple pointers coexist on one channel.
`x` and `y` are in **surface pixels**: the pixels of the raster the
surface presents, whatever size the page or window shows it at (see
[vocabulary.md](vocabulary.md)).

**Wheel.** A `KIND_WHEEL` record is a pointer event like any other,
with a position, buttons and modifiers, so a consumer hit-tests it the
same way. `wheel_unit` says what `dx` and `dy` count:

| `wheel_unit` | `dx`, `dy` | Source |
|---|---|---|
| `WHEEL_PIXELS` (0)  | eighths of a surface pixel | a trackpad's smooth scroll |
| `WHEEL_DETENTS` (1) | 1/120 of a detent, the unit of USB HID high-resolution wheels and evdev's `REL_WHEEL_HI_RES` | a wheel with notches |

Signs follow the W3C `WheelEvent`: positive `dy` scrolls toward the
end (content moves up), positive `dx` toward the right. A detent is
the device's unit; how many lines one scrolls is the consumer's own
metric. A producer sums what arrives between two of its steps into at
most one wheel record per pointer and unit, carrying the last
position; a sum past the record's range continues in a further record
and is never clamped. On every other kind `wheel_unit`, `dx` and `dy`
are zero, and `pointer::decode` refuses a record that says otherwise
or names an unknown unit.

| Producer | Wheel mapping |
|---|---|
| `wasm_browser_pointer` | the page's `wheel` event: pixel deltas scaled to surface pixels, line deltas as detents, page deltas as the surface's height in pixels; a wheel with Ctrl held is the browser's zoom and is not forwarded |
| `linux_pointer` | `REL_WHEEL_HI_RES` / `REL_HWHEEL_HI_RES` as they are; `REL_WHEEL` / `REL_HWHEEL` times 120 from a device that sends no high-resolution code (the kernel sends both from one that does); evdev's positive `REL_WHEEL` is away from the user, so `dy` is its negation |
| `linux_display` (window) | the window's line scroll as detents, its smooth scroll as pixels divided by the window's `scale`; a window reports the way content moves, so both axes change sign |

### `TextEvents` — `crates/fluxor-abi/src/contracts/input/text.rs`

What the platform's text machinery did, for an application that draws
its own text fields. Records are length-prefixed and the content type
is streamed: a consumer keeps one record's worth of carry buffer and
reassembles a split record.

```text
[msg: u8] [flags: u8] [len: u16 LE] [target: u32 LE] [payload …]
```

`target` is the accessibility node being edited, or `NO_TARGET` for the
application's own focused text field.

| `msg` | Payload | Meaning |
|---|---|---|
| `COMMIT`  | UTF-8 text, 1 to 1,024 bytes | insert at the target's selection, replacing it; flag `CONTINUES` when the next COMMIT continues the same insert |
| `COMPOSE` | `[hl_start u16][hl_end u16]` then the preedit | an input method's composition in progress, replacing the previous preedit; flags `START` on the first record and `END` on the last, which carries no preedit. `hl_start..hl_end` is the highlighted range |
| `DELETE`  | `[before u32][after u32]` | delete the selection if it is not empty, else that many scalar values before and after the caret |
| `SELECT`  | `[anchor u32][focus u32]` | the user moved the selection in the platform's field |

Offsets and counts are Unicode scalar values: not UTF-16 code units,
not bytes, not grapheme clusters. Text longer than 1,024 bytes is
split at scalar boundaries into COMMITs with `CONTINUES` on all but
the last. A preedit is display only; what a composition produced
arrives as a COMMIT after its `END`.

A record with invalid UTF-8, a length past its limit, an empty COMMIT,
an `END` carrying a preedit, or a COMPOSE with no `START` before it is
dropped together with the composition in progress, and counted.
`text::parse` and `text::Sequence` hold these rules for every
consumer.

| Producer | Source |
|---|---|
| `wasm_browser_accessibility`, `text` port | the focused element of the page's mirror: `beforeinput`, composition events and selection changes, translated; `target` names the mirrored node |
| `linux_display` (window), `text` port | text a key press typed, as a COMMIT; an input method's preedit as COMPOSE and its result as a COMMIT; `target` is `NO_TARGET` |

#### Keys and text, never twice

Every key reaches the application as a key record. Text reaches it as
text records. `KEY_TEXT` on a key record says that key's effect
already arrived as text. The consumer rule is the same on every
platform:

- While the consumer's own text target has focus, it applies
  `TextEvents` and ignores the editing effect of `KEY_TEXT` keys. A key
  without the flag is the consumer's to act on, editing keys included:
  an unflagged Backspace deletes, an unflagged Enter in a multi-line
  field inserts a line break, unflagged arrows move the caret.
- With no text target focused, it handles keys as keys whatever the
  flag.

So a platform with a native text field (the browser's mirror) flags
what the field did, deletions and pastes included. A platform without
one (the Linux window) flags only a key press that produced a COMMIT:
text with no control character while neither Ctrl nor Meta is held.
Backspace, Enter and shortcuts arrive unflagged there and the
application does the rest from key records. While an input method is
composing, keys produce no key record on either platform.

### Accessibility — `crates/fluxor-abi/src/contracts/accessibility.rs`

An application that draws its controls into a raster publishes them as
a tree, so a platform can make them reachable: mirror them for
assistive technology, place a text field for an input method, open a
soft keyboard.

`AccessibilityTree` (application to platform) carries length-prefixed
records: `TREE` (the batch replaces the whole tree), `NODE` (upsert by
id: parent, order, role, states, bounds, a range, a selection, and
name, value and description strings), `REMOVE` (a node and its
subtree), `FOCUS`, `ANNOUNCE`, and `APPLY`, which ends a batch and
carries the application's revision. A batch is applied whole or not at
all: a node whose parent is not in the tree, a cycle, more nodes than
the consumer's `max_nodes`, or any record the contract refuses rejects
the batch and the consumer keeps the tree it had
(`fluxor_sdk::accessibility::TreeCheck` holds the rule). Bounds are in
1/64 of a surface pixel. Roles are the `ROLE_*` constants, positions in
`ACCESS_ROLES`, each the ARIA role of the same name.

A node with `STATE_SECRET` never carries its value: the secret stays
in the application, and the node's `value_now` carries its length so
offsets and "n characters" still work.

`AccessibilityActions` (platform to application) carries fixed 12-byte
records: `ACTIVATE` (assistive technology pressed the node), `FOCUS`
(focus moved to a node, or left the surface), `SET_VALUE` (a range was
adjusted) and `RESYNC` (the platform has no tree it trusts; the
application answers with `TREE`, every node, `FOCUS` and `APPLY`).
Keys are never actions: Enter on a focused button arrives as a key
record and is the application's to handle. Text edits are not actions
either; they arrive on `TextEvents` naming the node.

| Consumer of the tree | What it does with it |
|---|---|
| `wasm_browser_accessibility` | mirrors it into the page as elements laid over the canvas; see [wasm_browser_host.md](wasm_browser_host.md) |
| `linux_display` (window), `tree` port | allows the window's input method while the focused node is editable and places it at the node's bounds; no mirror |

### `GamepadEvents` — `crates/fluxor-abi/src/contracts/input/gamepad.rs`

Fixed 16-byte frame modelled on the W3C Gamepad API: up to 16 digital
buttons plus up to 4 analogue axes per device, delivered as full state
snapshots. The canonical producer pattern is one snapshot per step
when state has changed, plus an idle snapshot roughly every 16 ms so
consumers can distinguish a held button from a stale channel.

### `MidiEvents` — `crates/fluxor-abi/src/contracts/input/midi.rs`

Fixed 4-byte frame carrying pre-decoded MIDI 1.0 channel-voice
messages: `[event_kind, channel, data1, data2]`. Producers include
browser Web MIDI, Linux ALSA seq, and class-compliant USB-MIDI hosts;
symmetric output drivers consume the same shape.

### Button wire — `crates/fluxor-abi/src/contracts/input/button.rs`

One byte per debounced state transition (`0x01` pressed, `0x00`
released), carried on `OctetStream` so untyped sinks can also tap a
button stream. Producers emit only debounced transitions, never
duplicates, so the timing logic (click counting, long-press dwell)
lives in exactly one place: `modules/foundation/gesture`.

### Action wire — `crates/fluxor-abi/src/contracts/input/action.rs`

A pure conduit for application-chosen semantic verbs. A control
carries an opaque action id string (`next`, `prev`, `toggle`, or any
app-specific verb); the producer hashes it with FNV-1a32 and emits the
hash as the FMP command type. Only the hash travels on the wire; the
consumer matches the same hash of the same string, so the two sides
agree without a shared vocabulary table. Fluxor carries no verb
vocabulary of its own.

### `SurfaceTraits` — `crates/fluxor-abi/src/contracts/input/surface_traits.rs`

Fixed 24-byte environment-plane record: viewport geometry, derived
orientation and size class, present input modalities, audio output
config, and the device pixel ratio. Published by the host platform
authority (`wasm_browser_surface_traits`, `linux_surface_traits`,
`panel_surface_traits` on bare metal); a module that wants to adapt to
its surface wires an input port to it. Modules that ignore it keep
static-config behaviour, so the contract is additive.

The viewport is in **logical pixels** (CSS pixels in a browser); size
classes key on it. Byte 22, `dpr_eighths`, is how many **surface
pixels** a producer renders per logical pixel for its raster to be
presented 1:1, in eighths: 8 is 1x, 12 is 1.5x, 18 is 2.25x. A producer
renders at `viewport x dpr_eighths / 8`. Zero means the authority
reports no ratio and a consumer keeps the one it is configured with. A
change of ratio moves the record's `epoch` like a resize.

| Authority | `dpr_eighths` |
|---|---|
| `wasm_browser_surface_traits` | the page's device pixel ratio, rounded to the nearest eighth, at least 1 |
| `linux_surface_traits` | 8: `linux_display` takes a raster of the viewport's own extent and magnifies it by its integer `scale` itself |
| `panel_surface_traits` | its `dpr_eighths` param (default 8), which a board declares together with the viewport; 0 for a panel with no display |

Byte 23 is zero; `surface_traits::decode` refuses a record where it is
not, and a consumer reads the record's fields through it.

## 3. Capability declarations

Source: `contracts/src/vocabulary.rs` (`CAPABILITY_NAMES`), enforced
at manifest parse time in `tools/src/manifest.rs` (case-insensitive
match, canonicalised to lowercase).

The registry's input-side names:

- `input.mapper` — module translates raw source input into another
  input surface or semantic commands
- `input.gamepad` — gamepad source
- `input.virtual` — software-synthesised source (no physical sensor)
- `input.remote` — source delivered over a transport from another peer
- `midi.input` / `midi.output` — MIDI drivers, paired with the
  `MidiEvents` content type
- `input.text` — the `TextEvents` surface. Port-scoped: the build maps it
  from the content type and checks every such edge, refusing two
  producers into one input (their records would interleave)
- `accessibility.tree` — the `AccessibilityTree` surface. Port-scoped in
  the same way, with one fact, `max_nodes`: the producer's largest tree
  must not exceed what the consumer holds

Capability names express role intent; the per-port `content_type`
declarations express data shape. Most input modules are matched by
content type alone and declare no capability names.

## 4. Roles

Three input roles sit above the surface family:

- **Source** — captures raw source events or state and encodes no
  application semantics. A button driver emits debounced transitions;
  it does not emit `play` or `pause`. Per-platform drivers expose the
  same wire shape (`wasm_browser_keyboard` and a hardware scan-code
  reader both emit `KeyEvents`), so downstream modules are
  platform-agnostic.
- **Mapper** — translates raw source input into consumer-facing
  input or semantic commands, and owns all timing and binding
  knowledge. `modules/foundation/gesture` consumes button bytes and
  emits FMP commands (`next`, `prev`, `toggle`, `select`,
  `long_press`, `on`, `off`, remappable per graph);
  `wasm_browser_touch_gamepad_overlay` consumes `PointerEvents` and
  emits `GamepadEvents`.
- **Consumer** — executes semantic commands or consumes mapped state,
  without depending on whether input was physical, virtual, local, or
  remote.

Sources and mappers are replaceable; application modules consume the
resolved surface only.

### Safety boundary

Fluxor's graph-scheduled input path is not a substitute for
hardware-rated safety interlocks. A graph-level emergency-stop binding
is appropriate for application-logic stop behaviour (release motors,
surface a fault, refuse new commands). A safety-rated stop guarantee
(IEC 61508 / ISO 13849 SIL or category ratings) must be enforced in
hardware or by a safety-rated subsystem outside the graph. Carrying
the signal on these surfaces is fine; relying on them as the only
enforcement path is not.
